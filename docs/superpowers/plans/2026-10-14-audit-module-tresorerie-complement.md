## B. Bugs confirmés par lecture et/ou exécution (citations exactes)

1. **`virement.py::executer_virement` — `generer_mouvement_debit`/`generer_mouvement_credit` non importés.** Aucun import de ces deux noms dans tout le fichier (`virement.py:1-8`), utilisés aux lignes `virement.py:70` et `virement.py:81`. → `NameError` certain si ce chemin est atteint.
2. **`virement.py::executer_virement` — `Virement.date` jamais fourni.** `Virement.date` est un `DateField` requis sans défaut (`models.py:134`). L'appel `Virement.objects.create(...)` (`virement.py:58-66`) ne passe pas `date=`. Confirmé par exécution : `pytest tresorerie/tests/test_services.py::test_virement_service_executer_virement` → `django.db.utils.IntegrityError: (1048, "Column 'date' cannot be null")`.
3. **`virement.py::executer_virement` — `Mouvement.annee_scolaire_id` jamais fourni.** `Mouvement.annee_scolaire` est une FK requise sans défaut (`models.py:240-244`, `on_delete=RESTRICT`, pas de `null=True`). Les deux appels à `generer_mouvement_debit`/`generer_mouvement_credit` (`virement.py:70-77`, `81-88`) ne passent pas `annee_scolaire_id`, qui vaudra `None` par défaut dans la signature de `compte.py` → `IntegrityError: Column 'annee_scolaire_id' cannot be null` attendu dès que les bugs 1 et 2 seront corrigés (non vérifié à l'exécution faute d'avoir corrigé 1 et 2, mais déduit sans ambiguïté de la lecture des deux signatures).
4. **`views.py::VirementViewSet.valider`/`annuler` — fonctions de service inexistantes.** Appellent `virement_service.valider_virement` (`views.py:99`) et `virement_service.annuler_virement` (`views.py:123`). `virement_service` (namespace défini `virement.py:136-141`) n'expose que `executer_virement`, `get_categorie_sortie_par_defaut`, `get_categorie_entree_par_defaut`, `calculer_solde_compte` — ni `valider_virement` ni `annuler_virement` n'existent dans tout `virement.py`. → `AttributeError` certain sur chaque appel à ces deux actions.
5. **`encaissement.py::creer_encaissement` — `generer_mouvement_credit` non importé.** Aucun import de ce nom dans le fichier (`encaissement.py:1-9`), utilisé à la ligne `encaissement.py:56`. Confirmé par exécution : `test_encaissement_service_creer_encaissement` → `NameError: name 'generer_mouvement_credit' is not defined`.
6. **`encaissement.py::annuler_encaissement` — `generer_mouvement_debit` non importé.** Même constat, utilisé à la ligne `encaissement.py:323`. Non testé isolément mais même cause racine que le bug 5 (même fichier, mêmes imports manquants).
7. **`encaissement.py::imputer_encaissement` — `F` non importé.** Le fichier importe `Sum` (`encaissement.py:4`) mais jamais `F` ; `F('montant_paye')` est utilisé à la ligne `encaissement.py:267`, dans la branche `cible == ECHEANCE`. → `NameError` certain dès qu'une imputation cible une échéance (cas majoritaire en pratique).
8. **`arrete_caisse.py::calculer_solde_theorique_caisse` — faute de frappe `movimentos_filter`.** Le dictionnaire est défini comme `mouvements_filter` (`arrete_caisse.py:44`) mais référencé comme `movimentos_filter` à la ligne `arrete_caisse.py:53`, exécutée dès que `date_arrete` est fourni (toujours vrai, c'est un paramètre requis). Confirmé par exécution : `test_arrete_caisse_service_creer_arrete` → `NameError: name 'movimentos_filter' is not defined`. **Bloque toute création d'arrêté de caisse via ce service.**
9. **`categorie_mouvement.py` — nom de fonction accentué.** `créer_categorie_mouvement` (`categorie_mouvement.py:10`, `categorie_mouvement_service` ligne 81) au lieu de `creer_categorie_mouvement` (convention ASCII utilisée partout ailleurs dans le module). Confirmé par exécution : `test_categorie_mouvement_service` → `AttributeError: 'types.SimpleNamespace' object has no attribute 'creer_categorie_mouvement'. Did you mean: 'créer_categorie_mouvement'?`. Non exploité par l'API actuellement (latent).
10. **`dashboard.py::get_ecarts_caisse_importants` — variable de boucle incorrecte.** `for arrete in arretes:` (`dashboard.py:193`) mais le corps (`dashboard.py:199-203`) accède à `arretes.solde_theorique`, `arretes.solde_physique`, `arretes.ecart`, `arretes.fait_par`, `arretes.valide_par` (le QuerySet au lieu de l'élément de boucle `arrete`). → `AttributeError` certain si la liste n'est pas vide, **masqué silencieusement** par le `try/except Exception: return []` englobant (`dashboard.py:179-210`).

13. **`annuler_encaissement`/`annuler_depense` — auteur de l'annulation jamais tracé.** Les deux fonctions codent en dur `cree_par_id=None` (`encaissement.py:331`, pattern identique dans `depense.py`) avec un commentaire "à remplir par l'appelant", alors que leurs signatures respectives (`annuler_encaissement(encaissement_id)`, `annuler_depense(depense_id)`) ne reçoivent aucun paramètre permettant à l'appelant de le faire.

## C. Bugs suspectés nécessitant une vérification supplémentaire (non confirmés à 100 % par lecture seule)

- **`BilletageViewSet` exposé en `ModelViewSet` complet** (point du tableau A) : je n'ai pas vérifié si un `serializer`/permission additionnel restreint en pratique l'écriture (`BilletageSerializer` non inspecté en détail) ; à confirmer avant de considérer le contournement comme pleinement exploitable.
- **`imputer_encaissement`, branche `FRAIS`** (`encaissement.py:220-249`) : le calcul `inscription_actuelle` semble mort/sans effet, mais je n'ai pas tracé si une validation équivalente existe ailleurs (ex. au niveau serializer ou permission) qui rendrait ce code redondant plutôt que lacunaire — à vérifier avant correction.
- **`test_effectuer_paiement_salaire_absence_mouvement_orphelin_echec`** échoue avec `rh_paie.models.SalaireAdministration.DoesNotExist` — ce test touche `tresorerie/services/services.py::effectuer_paiement_salaire`, qui est le chemin déjà identifié dans l'audit RH & Paie comme "service mort, jamais appelé par l'API réelle" ; la cause exacte de ce `DoesNotExist` (fixture de test vs bug de service) n'a pas été creusée ici, car elle recoupe un périmètre déjà couvert par l'audit RH & Paie du même jour.
- **Permissions (`TresoreriePermission`, `TresorerieValidationPermission`)** : je n'ai pas audité leur contenu dans cette passe (hors périmètre explicite de la mission reçue) — à faire si une passe sécurité/RBAC dédiée est demandée sur ce module.
- **Protection "mouvement validé/comptabilisé" (`Mouvement.valide`)** : contrairement à `Depense`/`Encaissement`/`Virement`/`ArreteCaisse` (qui ont tous un garde `save()`/`delete()` basé sur `editable_statuses`/`deletable_statuses`), **`Mouvement` lui-même n'a aucun tel garde** — son champ `valide` (défaut `True`, `models.py:253-256`) n'est vérifié par aucune surcharge `save()`/`delete()` sur le modèle. Un `Mouvement` peut donc être modifié ou supprimé directement via l'ORM/API sans aucune protection, y compris un mouvement déjà utilisé par un `Encaissement`/`Depense`/`Virement` validé — à confirmer si `MouvementViewSet` (lecture seule, `views.py:134`) est le seul point d'accès API, ce qui limiterait le risque côté API tout en le laissant ouvert côté admin Django/scripts.
